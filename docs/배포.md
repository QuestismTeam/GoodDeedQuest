# 배포 안내

팀원용 문서입니다. 무엇이 바뀌었고 앞으로 어떻게 일하면 되는지를 설명합니다.
AWS 나 Docker 를 몰라도 읽을 수 있게 썼습니다.


---

## 0. 먼저 결론

1. **로컬 개발 방식은 안 바뀌었습니다.** `docker compose up -d` 를 치면 예전처럼 DB 만 뜹니다.
2. **`dev` 브랜치에 머지하면 7분 뒤 서버에 자동으로 반영됩니다.** 아무도 서버에 들어갈 필요가 없습니다.
3. 서버 주소는 **https://gooddeedquest.duckdns.org** 입니다.

아래는 이게 어떻게 되는 건지, 그리고 무엇을 조심해야 하는지에 대한 설명입니다.

---

## 1. 배포 과정 — 여기까지 어떻게 왔나

내 노트북에서만 돌던 프로젝트를 인터넷에 띄우기까지 여덟 단계를 거쳤습니다.
**각 단계는 앞 단계에서 생긴 문제를 푸는 순서로 이어집니다.**

### 1단계. 코드를 상자에 담았다 — `Dockerfile`

**문제**: 내 노트북에서는 도는데 남의 컴퓨터에서는 안 됩니다.
파이썬 버전이 다르고, `ffmpeg` 이 안 깔려 있고, 한글 폰트가 없습니다.

**해결**: 필요한 걸 전부 적어둔 설명서를 만듭니다. 이게 `Dockerfile` 입니다.

```dockerfile
FROM python:3.12-slim
RUN apt-get install -y ffmpeg fonts-nanum
COPY backend ./backend
COPY ai ./ai
```

이 설명서대로 만들어낸 결과물이 **이미지**입니다. 이미지를 실행하면 **컨테이너**가 됩니다.
붕어빵 틀이 이미지, 붕어빵이 컨테이너라고 보시면 됩니다.

여기서 예상 못 한 일이 하나 있었습니다. `backend` 와 `ai` 를 따로 담으려다 실패했습니다.
이유는 [3-4](#3-4-도커-이미지가-왜-하나인가) 에 적었습니다. **둘이 서로를 임포트하고 있습니다.**

### 2단계. 여러 상자를 한 번에 띄웠다 — `docker-compose.yml`

**문제**: 상자가 하나가 아닙니다. backend, ai, celery 셋, redis. 매번 손으로 켤 수 없습니다.
게다가 DB 가 준비되기 전에 backend 가 뜨면 접속에 실패하고 죽습니다.

**해결**: 어떤 상자를 어떤 순서로 켤지 한 파일에 적습니다.

```yaml
depends_on:
  postgres:
    condition: service_healthy    # DB 가 "접속 받을 준비 됐다" 고 할 때까지 기다린다
```

여기서 팀원들 로컬 환경을 안 깨뜨리는 게 숙제였습니다.
그래서 새로 추가한 서비스에 `profiles: ["app"]` 이름표를 붙였습니다.
**평소에는 안 뜨고, `--profile app` 이라고 불러야만 뜹니다.**

### 3단계. AWS 에서 컴퓨터를 빌렸다 — EC2

**문제**: 24시간 켜져 있는 컴퓨터가 필요합니다. 내 노트북을 닫으면 서비스가 죽습니다.

**해결**: AWS 에서 `t3.small` 한 대를 빌렸습니다. 우분투가 깔린 컴퓨터 한 대라고 보면 됩니다.

여기에 **탄력적 IP** 를 붙였습니다. 그냥 두면 서버를 껐다 켤 때마다 주소가 바뀌는데,
탄력적 IP 는 고정 주소를 하나 붙잡아 두는 것입니다.

### 4단계. 데이터베이스를 밖으로 뺐다 — RDS

**문제**: DB 를 서버 안 컨테이너로 두면, 배포할 때마다 데이터가 날아갈 위험이 있습니다.
컨테이너를 지우고 다시 만드는 게 배포니까요.

**해결**: AWS 가 관리해 주는 PostgreSQL(RDS) 을 따로 만들고, 서버는 거기에 접속만 합니다.
**서버를 통째로 지우고 다시 만들어도 데이터는 그대로입니다.**

이 DB 는 인터넷에 열려 있지 않습니다. **EC2 에서 오는 접속만** 허용합니다.

### 5단계. 파일 보관소를 붙였다 — S3 + IAM Role

**문제**: 인증 사진과 숏폼 영상을 서버 디스크에 쌓으면 금방 꽉 찹니다.

**해결**: S3 에 올립니다.

그런데 여기서 보안 문제가 하나 생깁니다. S3 에 올리려면 AWS 에 "저 맞아요" 를 증명해야 하는데,
보통은 액세스 키를 `.env` 에 적어둡니다. **그 파일이 새면 남이 우리 S3 를 씁니다.**

그래서 **IAM Role** 로 바꿨습니다. 자세한 건 [5-4](#5-4-aws-액세스-키를-서버에-두지-않습니다) 에 있습니다.
한 줄로 말하면, **적어둘 비밀번호를 아예 없앴습니다.**

### 6단계. 이미지를 서버에 전달했다 — Docker Hub

**문제**: 만든 이미지를 어떻게 서버로 보낼까요? 1.86GB 짜리를 매번 복사할 수는 없습니다.

**해결**: **Docker Hub** 에 올립니다. 이미지 보관소입니다. 서버는 거기서 받아옵니다.

```bash
docker compose pull      # 새 이미지 받기
docker compose up -d     # 새 이미지로 다시 켜기
```

여기서 한 번 막혔습니다. **맥북은 arm64, EC2 는 amd64** 라 CPU 종류가 다릅니다.
맥에서 그냥 만든 이미지는 서버에서 안 돕니다. 그래서 만들 때 대상을 지정해야 합니다.

```bash
docker buildx build --platform linux/amd64
```

맥에서 이렇게 하면 20분 걸립니다. 지금은 GitHub 이 대신 만드는데, GitHub 컴퓨터가
원래 amd64 라서 몇 분이면 끝납니다.

### 7단계. 주소와 https 를 붙였다 — DuckDNS + nginx + certbot

**문제**: `http://13.x.x.x:8000` 은 외우기 어렵고, 자물쇠가 안 걸립니다.
안드로이드는 기본적으로 암호화 안 된 http 접속을 막습니다.

**해결**: 세 가지를 붙였습니다.

**DuckDNS** 로 무료 주소를 받았습니다 → `gooddeedquest.duckdns.org`

**nginx** 를 앞에 세웠습니다. 밖에서 오는 요청을 전부 먼저 받아서 안쪽 backend 로 넘깁니다.
그래서 backend 는 https 를 몰라도 됩니다. **nginx 가 자물쇠를 풀어서 넘겨주니까요.**

**certbot** 으로 인증서를 받았습니다. 무료이고 90일마다 자동으로 갱신됩니다.

### 8단계. 전부 자동으로 만들었다 — GitHub Actions

**문제**: 여기까지는 배포할 때마다 사람이 SSH 로 들어가서 명령을 쳐야 합니다.
빼먹거나 순서를 틀리기 쉽고, 사람마다 다르게 합니다.

**해결**: GitHub 에 **"이런 일이 생기면 이 명령들을 순서대로 쳐라"** 를 적어둡니다.
파일 두 개입니다.

`.github/workflows/ci-dev.yml` — **dev 에 푸시되면** 전체 스택을 띄워서 정말 도는지 검사합니다.

```
컨테이너 전부 띄우기 → 8000·8001 응답 확인 → 마이그레이션 →
카테고리 시드 → celery 작업 등록 확인 → 테스트
```

**전부 통과해야만** 그다음 `main` 으로 옮기는 단계로 넘어갑니다.

`.github/workflows/deploy.yml` — **main 에 푸시되면** 이미지를 만들어 Docker Hub 에 올리고,
EC2 에 SSH 로 들어가 새 이미지로 갈아끼웁니다.

여기서도 한 번 막혔습니다. GitHub 이 기본으로 주는 토큰으로 `main` 에 푸시하면
**`deploy.yml` 이 깨어나지 않습니다.** 워크플로우가 서로를 무한히 부르는 걸 막으려는 정책입니다.
그래서 개인 토큰(`GH_PAT`) 을 따로 만들어 씁니다.

### 정리

```
1. Dockerfile          어디서든 똑같이 도는 상자로 포장
2. docker-compose.yml  여러 상자를 순서대로 한 번에
3. EC2                 24시간 켜진 컴퓨터
4. RDS                 배포해도 안 날아가는 데이터
5. S3 + IAM Role       파일 보관, 비밀번호 없이
6. Docker Hub          만든 이미지를 서버에 전달
7. DuckDNS + nginx     외우기 쉬운 주소와 자물쇠
   + certbot
8. GitHub Actions      위 과정을 사람 없이
```

## 2. 내 일상 작업에 뭐가 달라지나

### 2-1. 로컬 개발 — 그대로입니다

예전과 똑같이 하시면 됩니다.

```bash
docker compose up -d
```

이러면 `postgres` 와 `redis` **두 개만** 뜹니다.

배포하면서 `docker-compose.yml` 에 서비스가 여러 개 늘었는데, 왜 안 뜰까요?
새로 늘어난 것들에는 이런 이름표가 붙어 있기 때문입니다.

```yaml
profiles: ["app"]
```

**이 이름표가 붙은 서비스는 `--profile app` 이라고 따로 불러줘야만 뜹니다.**
그냥 `docker compose up -d` 를 치면 무시됩니다. 그래서 예전 환경 그대로입니다.

백엔드와 AI 서버는 지금까지 하시던 대로 직접 띄우시면 됩니다.

```bash
python -m backend.main
```

```bash
python -m ai.main
```

여기서 자주 걸리는 게 하나 있습니다. 이런 에러가 나면요,

```
No module named 'backend'
```

**지금 폴더가 어디인지 확인하세요.** `frontend/` 안이나 `backend/` 안에서 치면 이 에러가 납니다.
파이썬이 `backend` 라는 폴더를 현재 위치에서 찾는데, `frontend/` 안에는 그런 게 없기 때문입니다.
**저장소 최상위 폴더**로 나와서 실행해야 합니다.

### 2-2. 배포 — dev 에 머지만 하면 끝입니다

```
내 브랜치 → PR → dev 머지
                   │
                   ├─ 자동: 코드가 제대로 도는지 검사        2~3분
                   │
                   ├─ 자동: 검사를 통과하면 main 으로 옮김
                   │
                   └─ 자동: 서버에 배포                     4분
```

**검사에서 하나라도 실패하면 그 자리에서 멈춥니다.** 깨진 코드가 서버까지 가는 일은 없습니다.
안심하고 머지하셔도 됩니다.

진행 상황은 GitHub 저장소의 **Actions** 탭에서 볼 수 있습니다.
초록 체크면 성공, 빨간 X 면 실패입니다. 실패한 걸 눌러보면 어느 단계에서 멈췄는지 나옵니다.

### 2-3. 테스트 — 이제 아무 노트북에서나 돌아갑니다

전에는 이런 일이 있었습니다.

일부 테스트가 **"DB에 1번 유저가 있다"** 고 가정하고 코드에 `user_id=1` 을 박아뒀습니다.
그런데 그 유저를 누가 지우자, 그 테스트들이 전부 "그런 유저 없다" 며 실패했습니다.
새로 클론받은 팀원 노트북에서는 아예 처음부터 실패했습니다.
더 나쁜 건, 몇 개는 실패 대신 **조용히 건너뛰어져서** 아무도 몰랐다는 점입니다.

지금은 테스트가 **자기가 쓸 유저를 직접 만들고, 끝나면 지웁니다.**
`backend/app/common/tests/factories.py` 가 그 일을 합니다.

```python
from backend.app.common.tests.factories import create_test_user, delete_test_user

class SomeTest(TestCase):
    def setUp(self):
        self.test_user_id = create_test_user()

    def tearDown(self):
        delete_test_user(self.test_user_id)
```

**새 테스트에 DB 유저가 필요하면 이걸 쓰세요.** 특정 ID 를 코드에 박지 마세요.

### 2-4. 실제 AI 를 부르는 테스트는 따로 뺐습니다

진짜 Gemini 를 호출하는 테스트가 섞여 있었습니다.
API 키가 없는 환경에서 이걸 돌리면, 실패할 때마다 다시 시도하느라 **11분 넘게** 걸렸습니다.

그래서 그런 테스트에 표시를 붙였습니다.

```python
pytestmark = pytest.mark.live_llm
```

평소에는 이걸 빼고 돌리시면 됩니다. 3~4초면 끝납니다.

```bash
pytest -m "not live_llm"
```

**실제 AI 응답까지 봐야 할 때만** 전체를 돌리세요.

```bash
pytest
```

## 3. 서버는 어떻게 생겼나

### 3-1. 전체 그림

```
        휴대폰 / 브라우저
              │  https
              ▼
    ┌──────────────────────┐
    │   EC2 (우리 서버 한 대) │
    │                      │
    │   nginx  ────────┐   │   문지기. https 를 풀어서 안으로 넘김
    │                  ▼   │
    │              backend │   API. 앱이 실제로 말을 거는 곳
    │                  │   │
    │                  ▼   │
    │                 ai   │   추천·숏폼 담당. 밖에서는 안 보임
    │                      │
    │   celery ×3          │   오래 걸리는 작업 처리
    │   redis              │   작업 대기줄
    └──────────┬───────────┘
               │
        ┌──────┴──────┐
        ▼             ▼
      RDS            S3
   (데이터베이스)   (이미지·영상)
```

**앱은 항상 backend 하고만 이야기합니다.** AI 서비스가 필요하면 backend 가 대신 불러줍니다.
AI 서비스는 인터넷에 열려 있지 않아서, 밖에서는 주소를 알아도 접근할 수 없습니다.

### 3-2. 각각이 뭘 하나

| 이름 | 하는 일 | 밖에서 접근되나 |
| --- | --- | --- |
| **nginx** | https 를 처리하고 요청을 backend 로 넘긴다 | ✅ 유일한 출입구 |
| **backend** | API 서버. 로그인·퀘스트·상점 | ❌ nginx 를 통해서만 |
| **ai** | 추천, 숏폼 생성 | ❌ backend 만 부를 수 있음 |
| **celery-worker** | 배지 지급 같은 주기 작업 | ❌ |
| **celery-beat** | "이제 그 작업 돌릴 시간이야" 알람시계 | ❌ |
| **celery-worker-shortform** | 숏폼 영상 만들기 | ❌ |
| **redis** | 작업 대기줄 | ❌ |
| **RDS** | PostgreSQL. 실제 데이터 | ❌ EC2 에서만 |
| **S3** | 사진·영상 파일 보관 | 파일 주소로만 |

### 3-3. celery 워커가 왜 세 개인가

`celery-beat` 는 **알람시계**입니다. 일을 하지 않습니다.
"10분 지났으니 보류 인증 재판정 돌릴 시간이야" 하고 대기줄에 넣기만 합니다.

`celery-worker` 와 `celery-worker-shortform` 이 **실제로 일하는 쪽**입니다.
그런데 왜 둘로 나뉘었을까요?

우리 코드에 Celery 앱이 두 개 있기 때문입니다.

```
backend.app.challenge.celery_app       ← 배지, 인증 재판정
backend.app.short_form.celery_app      ← 숏폼 영상 생성
```

**워커는 자기 앱에 등록된 작업만 처리합니다.** 하나로 합치면 다른 쪽 작업이 대기줄에
쌓이기만 하고 아무도 안 꺼내갑니다. 그래서 둘 다 띄워야 합니다.

숏폼이 "생성 중" 에서 안 넘어가면 `celery-worker-shortform` 을 먼저 확인하세요.

### 3-4. 도커 이미지가 왜 하나인가

보통은 backend 와 ai 를 각각 다른 이미지로 만듭니다. 우리는 그렇게 못 합니다.
**둘이 서로를 임포트하고 있기 때문입니다.**

```python
# backend/app/quest_verification/challenge.py:7
from ai.app.common.llm import get_gemini_model
```

```python
# ai/app/quest_recommend/nodes/volunteer_agent.py:5
from backend.app.common.database import SessionLocal
```

backend 는 ai 의 Gemini 설정을 가져다 쓰고, ai 는 backend 의 DB 접속을 가져다 씁니다.
**양방향입니다.**

그래서 backend 이미지에 `backend` 폴더만 담으면, 실행하자마자 `No module named 'ai'` 로 죽습니다.
반대도 마찬가지입니다.

해결은 간단합니다. **하나의 이미지에 둘 다 담고, 켤 때 명령만 다르게** 줍니다.

```yaml
backend:
  command: uvicorn backend.main:app --port 8000

ai:
  command: uvicorn ai.main:app --port 8001
```

같은 상자인데 여는 문만 다른 셈입니다.

## 4. 브랜치 규칙

```
내 브랜치  →  PR  →  dev  →  (자동) main  →  (자동) 서버
```

- **작업은 항상 새 브랜치에서** 합니다. `dev` 나 `main` 에 직접 커밋하지 않습니다.
- **`main` 은 사람이 건드리지 않습니다.** 검사를 통과한 `dev` 가 자동으로 옮겨갑니다.
- 커밋 메시지는 한 줄로 씁니다. 자세한 설명은 PR 본문에 씁니다.

```bash
git switch -c feat/내작업 origin/dev
```

```bash
git commit -m "feat: 퀘스트 인증 사진 회전 처리"
```

### GitHub 에 가끔 뜨는 노란 띠

`main had recent pushes` 라는 안내가 보일 때가 있습니다.
**자동 배포가 `main` 에 푸시해서 뜨는 것이고 정상입니다.** 배포할 때마다 뜹니다.

옆의 초록 버튼(`Compare & pull request`)은 **누르지 마세요.**
`main → dev` 방향으로 PR 을 만들려는 건데, 우리 흐름과 반대입니다.
잘못 머지하면 `dev` 가 옛날 커밋들을 끌어옵니다. 그냥 두면 몇 시간 뒤 사라집니다.

## 5. 하면 안 되는 것

### 5-1. `.env` 를 커밋하지 않습니다

비밀번호와 API 키가 들어 있습니다. **한 번 올라가면 지워도 git 기록에 남습니다.**

새 설정값이 필요하면 `.env.example` 에 **이름만** 추가하고, 실제 값은 각자 채웁니다.

### 5-2. 로컬 앱을 서버 DB 에 연결하지 않습니다

`.env` 의 `DATABASE_URL` 을 서버 DB 로 바꾸고 싶을 때가 있을 겁니다. 하지 마세요.
무슨 일이 일어나는지 구체적으로 적겠습니다.

**`pytest` 를 한 번 돌리면 시연 데이터가 날아갈 수 있습니다.**
테스트가 끝날 때 `delete_test_user` 를 부르는데, 이 함수는 유저를 참조하는
**모든 테이블에서** 그 유저의 행을 지웁니다. 지울 테이블 목록을 DB 스키마에서
직접 읽어와서 돌기 때문에 범위가 넓습니다.

**`alembic upgrade head` 를 습관적으로 치면 운영 DB 스키마가 바뀝니다.**

**시드를 다시 돌리면 카테고리나 상점 아이템이 두 벌이 됩니다.**

서버 데이터를 **보기만** 하려면 SSH 터널을 열고 DataGrip 으로 붙으세요.
개발용 데이터가 필요하면 `pg_dump` 로 로컬에 복사해서 쓰세요.

### 5-3. `--profile app` 을 개발용으로 쓰지 않습니다

```bash
docker compose --profile app up -d --build     # ← 평소엔 쓰지 마세요
```

이걸로 띄운 컨테이너에는 **내 소스 코드가 연결되어 있지 않습니다.**
빌드한 순간의 코드가 상자 안에 그대로 굳어 있어서, 파일을 고쳐도 컨테이너는 모릅니다.
반영하려면 매번 이미지를 다시 만들어야 합니다.

**서버와 똑같은 구성을 로컬에서 확인해야 할 때만** 쓰세요. CI 가 이 방식으로 검사합니다.

### 5-4. AWS 액세스 키를 서버에 두지 않습니다

서버는 **IAM Role** 로 S3 에 접근합니다.

키를 쓰는 방식은 이렇습니다. `.env` 에 아이디와 비밀번호 같은 문자열을 적어두고
매번 그걸 보여주면서 "저 맞아요" 하는 겁니다. 이 문자열이 새어나가면 남이 우리 S3 를 씁니다.

IAM Role 은 다릅니다. **EC2 가 AWS 에 "나 누구야?" 하고 물으면, AWS 가 이 서버에
붙여둔 역할을 확인하고 짧게 쓰고 버릴 임시 자격증명을 내려줍니다.**
적어둘 비밀번호가 애초에 없습니다.

그래서 서버 `.env` 에 `AWS_ACCESS_KEY_ID` 같은 값을 넣지 마세요.
**로컬 개발용으로는 여전히 필요합니다.** 로컬 PC 는 EC2 가 아니니까요.

## 6. 문제가 생겼을 때

### 6-1. 배포가 실패했다

GitHub 의 **Actions** 탭 → 빨간 X 클릭 → 어느 단계에서 멈췄는지 봅니다.

**"빌드 · 기동 · 테스트 검증"에서 멈췄다면 내 코드 문제일 가능성이 높습니다.**
로그를 열면 어떤 테스트가 왜 실패했는지 그대로 나옵니다.

그 뒤 단계("main 으로 자동 승격", "Deploy to EC2")에서 멈췄다면 배포 설정 문제입니다.
코드는 멀쩡하니 당황하지 않으셔도 됩니다.

### 6-2. 서버가 이상하다

```bash
ssh -i <키파일> ubuntu@<서버IP>
```

```bash
cd ~/gdq
```

먼저 컨테이너 상태를 봅니다.

```bash
docker compose ps
```

`STATUS` 에 **`Restarting`** 이 보이면 그 컨테이너가 켜지다 죽기를 반복하는 중입니다.
원인은 그 컨테이너 로그 맨 위에 있습니다.

로그를 봅니다.

```bash
docker compose logs -f --tail=0 backend ai
```

`--tail=0` 은 **빈 화면에서 시작해서 지금부터 오는 요청만** 보여줍니다.
앱을 켜놓고 이 창을 보면 어떤 API 가 호출되는지 실시간으로 흘러갑니다.
빠져나올 땐 `Ctrl+C` 입니다. 컨테이너는 안 죽습니다.

숏폼이 안 만들어지면 워커를 봅니다.

```bash
docker compose logs -f --tail=100 celery-worker-shortform
```

### 6-3. 로그에 404 가 잔뜩 보인다

정상입니다. 세 가지가 자주 보입니다.

```
GET /api/v1        404
```
`/api/v1` 자체는 주소가 아닙니다. `/api/v1/shop` 처럼 뒤가 붙어야 주소입니다.

```
GET /favicon.ico   404
```
브라우저가 탭에 띄울 아이콘을 찾는 겁니다. API 서버라 없습니다.

```
HEAD /             405
```
`405` 는 "그 주소는 있는데 그 방식은 안 받는다"는 뜻입니다.
`/` 는 `GET` 만 받도록 되어 있는데 `HEAD` 로 물어봐서 그렇습니다.

**셋 다 브라우저가 습관적으로 보내는 요청이라 무시하시면 됩니다.**

## 7. 자주 쓰는 명령

```bash
docker compose up -d
```
로컬 DB 와 redis 를 켭니다. **평소 개발은 이것만 있으면 됩니다.**

```bash
docker compose down
```
컨테이너를 내립니다. **데이터는 남습니다.**

```bash
docker compose down -v
```
데이터까지 지웁니다. **되돌릴 수 없습니다.** 로컬 DB 를 완전히 초기화할 때만 쓰세요.
서버 DB 와는 아무 상관이 없습니다. 지우고 나면 아래 두 개를 다시 돌려야 합니다.

```bash
alembic upgrade head
```
DB 표 구조를 최신으로 맞춥니다. 남이 만든 마이그레이션을 받았을 때도 실행합니다.

```bash
python -m backend.app.quest.seed_category
```
카테고리 기본 데이터를 넣습니다.

```bash
pytest -m "not live_llm"
```
실제 AI 호출을 뺀 빠른 테스트입니다.

## 8. 궁금할 만한 것

**Q. 내가 dev 에 머지하면 진짜 서버가 바뀌나요?**
네, 7분 뒤에 바뀝니다. 다만 검사를 통과해야만 넘어가므로 깨진 코드는 올라가지 않습니다.

**Q. 서버에 직접 들어가서 코드를 고쳐도 되나요?**
안 됩니다. 다음 배포 때 덮어써집니다. 항상 `dev` 를 거쳐야 합니다.

**Q. 발표 직전에 누가 머지하면 시연 서버가 바뀌나요?**
그래서 발표 하루 이틀 전에 자동 승격을 잠급니다. 그때부터는 `dev` 에 머지해도 서버가 안 바뀝니다.

**Q. 프론트엔드 APK 도 자동으로 만들어지나요?**
아니요. 앱 빌드는 Expo 클라우드에서 따로 돌립니다. 서버 배포와는 완전히 다른 경로입니다.

**Q. Expo Go 로 앱을 못 켜는데요?**
카카오·구글 로그인이 네이티브 기능이라 Expo Go 안에 들어 있지 않습니다.
`eas build --profile development` 로 만든 개발용 앱을 설치해야 합니다.
